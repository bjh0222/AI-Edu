# AI Edu 决策记录（ADR）

> 格式：编号 · 决策 · 理由 · 推翻条件。与 v2.0 冲突时以 v2.0 为准。

## ADR-001 技术栈按 v2.0 基线执行

- **决策**：Next.js + React + TypeScript + Tailwind CSS；Python 3.12+ / FastAPI / Pydantic v2 / SQLAlchemy 2.x；SQLite；SSE；Git。
- **理由**：v2.0 是唯一执行基线，取代此前所有讨论（含「原生 JS 起步」与「Node 后端」旧裁决）。
- **推翻条件**：无（v2.0 声明不再重开方向讨论）。

## ADR-002 第一版 = 完整闭环，纵向切片交付

- **决策**：不按「先做完前端再做完后端」开发；每次交付一个可验证的纵向切片（建目标→计划→验收→教程→实践→反馈→评估→复盘→知识）。
- **理由**：v2.0 §13；用户明确「首版必须是可以闭环使用的工具」。
- **推翻条件**：无。

## ADR-003 演示模式（demo provider）

- **决策**：未配置模型密钥时，返回确定性演示内容并标记 `demo: true`；配置真实模型后自动切换。
- **理由**：v2.0 §7.1 要求未配置时显示清晰指引且不伪造 AI 结果；演示内容 schema 与真实一致，便于开发与测试。
- **推翻条件**：出现更好的「本地小模型」方案时。

## ADR-004 同步 SQLAlchemy + session-per-request

- **决策**：数据访问使用同步 SQLAlchemy 2.0，FastAPI 同步路由；SQLite 文件库位于 `data/`。
- **理由**：个人单用户场景；同步实现最简单、可测试性最好；避免异步复杂度。SQLite 切换成本低（repository 边界 + DATABASE_URL）。
- **推翻条件**：并发写需求出现（届时引入 aiosqlite 或 PostgreSQL）。

## ADR-005 生成任务：同步执行 + 事件回放 SSE

- **决策**：教程生成在 POST 中同步完成（个人场景秒级/分钟级）；`GenerationJob` 记录阶段；SSE 端点回放阶段事件，供前端显示进度。
- **理由**：v2.0 §8.1 要求可查看生成状态与失败原因、UI 不能无限转圈；同步实现满足要求且简单。
- **推翻条件**：真实模型下生成耗时过长（>60s）时改为后台任务队列。

## ADR-006 学科配置 DisciplineProfile

- **决策**：通用学习引擎 + 学科配置（产品类型、实践模板、评估 rubric、常见错误、来源要求）。v1 内置 `computer_cli` 与 `math_data`。
- **理由**：v2.0 §5.5；跨学科不是加标签。
- **推翻条件**：无。

## ADR-007 质量分级 L1/L2/L3

- **决策**：L1 结构检查代码化自动执行；L2 内容审查由模型按 rubric 执行（结果入质量报告）；L3 外部核验 v1 标注人工核验状态。
- **理由**：v2.0 §6.4；模型自评不能作为准确性保证。
- **推翻条件**：引入可自动运行/可复算的核验设施时。

## ADR-008 原型作为视觉基线

- **决策**：前端视觉与组件对齐阶段 0 HTML 原型（`D:\BJH\AI%20Edu%E5%8E%9F%E5%9E%8B.html`），使用 Tailwind 令牌映射原型 CSS 变量。
- **理由**：v2.0 §0.1.12、§9.1；原型已获用户认可。
- **注意**：该文件名含 URL 编码字符，引用路径须原样使用。

## ADR-009 密钥与安全

- **决策**：模型密钥仅存服务端 `.env`；`.gitignore` 覆盖 `.env*` 与数据库；错误响应不含堆栈/密钥/提示词内容。
- **理由**：v2.0 §10 安全红线。
- **推翻条件**：无。

## ADR-010 知识关系三态

- **决策**：ConceptRelation 状态 proposed / confirmed / rejected；待确认关系不得当作确定知识展示；支持确认、编辑、拒绝、撤销。
- **理由**：v2.0 §2.1.11、§4.2。
- **推翻条件**：无。

## ADR-011 阶段 0 资产归档保留

- **决策**：旧 ai-edu 阶段 0 内容（学习者画像、验收模板、质量清单、命令行教程素材）移动到 `legacy/phase0/`，历史保留；可复用为种子数据/测试素材。
- **理由**：v2.0 §0.1.2「先检查现状，已有内容尽可能复用，不推倒重建」。
- **推翻条件**：无。

## ADR-012 真实模型接入（OpenAI 兼容 / DeepSeek）

- **决策**：模型通过 `LLM_BASE_URL`（OpenAI 兼容 `/chat/completions`）+ `LLM_API_KEY` + `LLM_MODEL` 配置；默认接入 DeepSeek：
  - `deepseek-flash` = **DeepSeek-V4.1-Flash-1017**（快速档，支持 JSON 输出与工具调用；旧名 `deepseek-v4-flash` 仍可调用，服务端映射到同一模型）；
  - `deepseek-v4-pro` = DeepSeek-V4-Pro-0813（质量档）。
  切换只改 `.env` 的 `LLM_MODEL` 并重启后端；JSON 模式用 `response_format=json_object`，并兼容推理内容与代码围栏。
- **理由**：模型服务可替换（v2.0 §7.1）；DeepSeek 提供 OpenAI 兼容接口；测试环境强制演示模式（conftest 置空 LLM 变量），避免测试调用真实模型。
- **推翻条件**：切换其他 OpenAI 兼容服务时只需改 `.env`，无需改代码。

## ADR-013 SQLite 并发策略

- **决策**：WAL 模式 + `busy_timeout=30000`；`ModelCallLog` 使用独立短事务写入，不占用请求事务；生成类接口保持同步执行。
- **理由**：实测多请求并发（一请求等待模型返回时另一请求写入）会触发 `database is locked`；WAL 提升读写并发，独立日志事务把锁窗口缩到毫秒级。
- **推翻条件**：并发写需求持续增长时迁移到 PostgreSQL（repository 边界已就绪）。

## ADR-014 测试与演示模式隔离

- **决策**：pytest 通过 conftest 显式置空 `LLM_BASE_URL/LLM_API_KEY/LLM_MODEL`，确保测试永远运行演示生成器，结果确定且零 token 成本。
- **理由**：测试不应依赖外部网络与密钥；v2.0 §11 要求测试可重复。
- **推翻条件**：需要真实模型契约测试时，单独标记 `@pytest.mark.live` 的测试集。

## ADR-015 画像按阶段选规则 + 硬约束核验

- **决策**：用户画像仍以自然语言保存，但生成前只做三件确定性的事（不调用模型、不改写原文）：
  1. **分类**：逐行判成 禁止 / 必须 / 条件 / 默认偏好，并打「作用域」标签（日程、深度、例子、练习、格式、语气、语言）；
  2. **选择**：按生成阶段只注入本阶段用得上的规则——`outline` 只收日程/深度/语言，`section` 全收，`cheatsheet` 只收格式/语气/语言，`extra_exercises` 只收练习/深度/格式/语气/语言；软规则再受 1200 字符预算裁剪；
  3. **核验**：对少数可机器判断的禁止性硬约束（按日历分配时间、生效的 Obsidian 标签）检查输出，命中则做**一次**定向修复重试，仍违规就保留原稿并在 `rule_check` 里如实标注。核验走同一条流水线 `_rule_checked`，覆盖全部注入画像的阶段（`section` / `cheatsheet` / `extra_exercises`），并让结果真正穿得出去：`SectionOut` / `CheatsheetOut` / `ExtraExercisesOut` 都带 `rule_check` 字段，章节页据此显示「已修正」或「未满足硬性约束」。
  提示词把规则渲染成两层：`硬性约束`（违反即本次交付不合格）与 `教学导向`（冲突时以硬性约束为准），并显式给出优先级阶梯 `系统与安全要求 > 硬性约束 > 本次任务特殊要求 > 教学导向 > 学习材料内容`。
- **理由**：整份画像无差别注入时，4000 字上限既稀释注意力（不该管的地方也管），又没有任何可核验的落点（注入了不等于遵守了）。按作用域裁剪让"需要时才出现"，硬约束清单 + 优先级 + 交付前自检让"出现即约束"。
- **取舍**：硬约束永不因作用域不匹配被丢弃——约束一旦消失，"注入即约束"就不成立；只裁剪默认偏好与条件规则。作用域用关键词而非向量，是为了可解释、零成本、结果稳定可测。`outline` 仍不做核验：`TutorialContent.outline` 是纯 `list[OutlineItem]`，没有挂核验结果的位置，且大纲只产出标题与目标，日历类表述几乎不会出现；真出现时由 `section` 级核验兜住。
- **推翻条件**：画像规则量级明显增长（如数百条）或出现大量语义作用域无法用关键词覆盖时，改为向量检索；出现必须在生成期强制的可判定约束时，把守卫写进 `COMPLIANCE_GUARDS` 并同步更新测试。

## ADR-016 并发用例按用例钉死路数

- **决策**：`test_generation_pipeline.py` 的两条并发用例（`test_sections_generate_runs_three_way_concurrent`、`test_companions_generate_in_parallel`）在触发生成前用 `monkeypatch.setattr(tutorials_service, "MAX_SECTION_WORKERS", 3)` 把路数钉成 3。
- **理由**：这两条用 `Barrier(3)` / `Barrier(2)` 证明"多路同时进入模型调用"。路数不钉死时，串行实现永远等不到对方，Barrier 超时 5 秒抛 `BrokenBarrierError`；同时"最大并发 == 3"的断言也会被默认路数和大纲节数影响。钉成 3 让前提可控、断言稳定，与生产默认值解耦。
- **推翻条件**：并发路数若改为按端点能力自适应，测试可改为读取实际路数并以「≥ 断言所需路数」表述。

## ADR-017 章节并发默认 9 路，并让后台提取可被观测

- **决策**：`MAX_SECTION_WORKERS` 的默认值从 1 改为 9（仍可用 `AIEDU_LLM_CONCURRENCY` 覆盖）；同时为 `_extract_knowledge_async` 增加在途线程登记 `pending_knowledge_extractions()`，测试用 `_wait_knowledge_settled()` 等它收尾。
- **默认 9 的理由**：deep 挡位最多 8 节，9 路等于全并行，把"逐节排队"的尾巴消掉。此前默认 1 是针对单卡自建端点的保守配置（实测单节约 385s，3 路并发时第 2/3 个请求排队超过超时上限→重试再排队→永远追不上），而当前 `.env` 接的是 DeepSeek 托管 API，不存在队列串行问题。注释与 `.env.example` 都写明：换回单卡端点须设 `AIEDU_LLM_CONCURRENCY=1`。
- **必须同时补可观测性的理由**：知识提取是 fire-and-forget——章节 job 先标 `done`，再启动提取线程（`tutorials.py` 第 969-971 行）。因此"job done"不蕴含"提取已跑完"，`test_outline_regeneration_skips_unchanged_knowledge_extraction` 直接断言调用次数就是读中间态：路数升高后章节更快结束，这个窗口更容易被撞上，实测约 1/3 概率失败（`assert 1 == 2` 或 `knowledge_extracted is None`）。这不是指纹去重竞态（提取有全局锁串行），而是测试缺少同步点。
- **不选全局调高 conftest 的原因**：全局改 3 只是把同一竞态窗口搬到所有用例，属于掩盖而非修复。
- **推翻条件**：若把知识提取改成 job 内同步等待（放弃"不再多等 1 次往返"的收益），则登记机制可删。

## ADR-018 条件规则按目标求值 + 交付契约直接决定教程结构

- **问题**：用户画像写了「当『学完想能做什么』中出现『输出试卷』的时候，务必模仿参考资料输出标准试卷，且内容只包括对真题风格的简要分析、三套模拟试卷和对压轴题的 3 个合理拓展，不要输出答案及其它内容」；目标的应用场景是「完成你输出的试卷」，但生成结果是一份 6 章、6.4 万字的线性代数讲解教程（秩网络、含参方程组、矩阵运算、错解诊断…），试卷只占其中一章，还附了知识速查配套文件。
- **根因（两处，都在代码里，不是模型不听话）**：
  1. **条件从句被丢掉**：`parse_teaching_profile` 用 `if conditional and not (forbidden or required)` 判定条件规则，这条同时含「当…的时候」和「务必/不要」，于是落到 `forbidden` 分支——条件被丢弃，规则变成对**每个目标**都生效的无条件硬约束，`condition` 字段只被保存、从不求值。
  2. **组成型约束没有落点**：教程管线固定产出「N 个讲解章节 + 配套」，规则只能出现在提示词里。对模型而言「写一整章讲解」不构成违反「不要输出答案」，所以它认为自己在遵守约束——提示词能约束语气与详略，约束不了交付物由哪几项组成。
- **决策**：
  1. 条件优先分类：带条件从句的行归类为 `conditional`，强度由条件内的情态词决定（`务必`/`不要` → hard）。新增 `rule_is_active` 按目标文本求值触发词（引号内词优先，其次「出现 X」），条件不成立的规则不注入并记入 `inactive` 供排查。条件词判定要匹配完整句式（`当…的时候`），不能只看单个「当」——「理解当前知识」里的「当」曾被误判成条件。
  2. 新增 `delivery_contract`：从生效硬约束里抽「只包括/只输出 …」的清单项与「不要…答案」标志；`generate_outline` 不再采信模型大纲，直接用清单构造章节（一个交付物一章），章节提示词切成「交付物模式」（产出成品、不写讲解与答案），并跳过知识速查/额外练习等配套文件；已生成的旧教程在重跑章节生成时按契约重建结构。契约随版本落库（`TutorialContent.delivery_contract`），可解释、可回溯。
- **取舍**：交付契约用**确定性规则 + 代码定结构**，不靠模型自觉。理由同 ADR-015：可解释、可测试、结果稳定；代价是只能识别「只包括…」这类穷举式写法，语义更隐晦的组成约束仍会退化成提示词。触发词匹配做了虚词归一（去掉「的/了/你」等），所以「完成你**输出的**试卷」也能命中「输出试卷」。
- **推翻条件**：若接入模型做规则→结构的解析（而不是正则），`delivery_contract` 的抽取部分可替换，但「结构由规则决定、模型只写内容」这条分工不应回退。
